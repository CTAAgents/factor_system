## 1. 背景

### 1.1 问题陈述

DuckDB 并发锁问题持续影响 FTS 正常开发与运行，具体表现：

| # | 现象 | 影响 |
|:--|:-----|:-----|
| P0 | 演化进程存活期（数小时）持有写锁，**连只读查询亦被阻塞** | 开发期并行操作、归档脚本、CLI 查询全部被锁住 |
| P0 | `scripts/` 脚本与调度器 job 对同一 `.duckdb` 文件并发写，抢文件锁 | `ConcurrentTransactionException`，重试放大延迟，极端失败 |
| P1 | checkpoint/写事务期间只读查询被文件锁阻塞 | 回测/因子加载随机卡顿 |
| P1 | 测试全量回归读锁无限阻塞（后台 scheduler 写库时） | 回归 timeout，conftest 被迫 mock 宏观源规避 |

### 1.2 根因分析（关键）

FTS 的锁痛点并非单一原因，拆解为三层：

```
┌─────────────────────────────────────────────────────────────────────┐
│ 根因 1（主因）：写连接生命周期与进程绑定                              │
│   data_futures.DuckDBWriter 全局单例在演化进程存活期持有写锁         │
│   （plans/29 明确登记：连只读亦被锁，登记为远期遗留未改造）            │
├─────────────────────────────────────────────────────────────────────┤
│ 根因 2：跨进程写协调缺失                                              │
│   scripts/ 与 scheduler job 无跨进程写互斥协议，各自直接写同一文件     │
├─────────────────────────────────────────────────────────────────────┤
│ 根因 3（DuckDB 固有）：单文件嵌入式引擎的锁模型                       │
│   任何可写连接对文件持有锁；1.1+ 的 lock_configuration 缓解但仍存在    │
│   checkpoint/提交期间的读阻塞窗口                                      │
└─────────────────────────────────────────────────────────────────────┘
```

**关键判断：根因 1、2 是「连接生命周期与写协调」问题，与数据库选型无关。即使换成 SQLite/PostgreSQL，若写连接长期存活、无跨进程写互斥，同样会产生锁阻塞。** 因此「弃用 DuckDB」并不直接等价于「根治锁问题」。

### 1.3 当前存储资产实测（2026-08-13）

| 库 | 域 | 文件大小 | 写入特征 | 读特征 |
|:---|:---|:--------|:--------|:-------|
| `data/fts_history.duckdb` | L2 行情 | **195.5 MB** | 追加式，批量 COPY，低频 | 全链路读取核心 |
| `data/factor_catalog_futures.duckdb` | L3 因子（期货） | 13.5 MB | 低频（晋升/审查） | CLI/回测查询 |
| `data/factor_catalog_stock.duckdb` | L3 因子（股票） | 25.5 MB | 低频 | CLI/回测查询 |
| `data/factor_catalog.duckdb` | L3 旧库 | 82.8 MB | 已弃用未清理 | — |
| `data/state.duckdb` | L4 运行状态 | 34.8 MB | **高频小写（演化/组合/meta_loop/extractors 5 模块进程级共享，每 save() 一次）** | 冷启动/对账 |
| `memory/portfolio/simulated/sim_state.db` | 模拟仓 | — | SQLite WAL（已上线） | — |

## 3. 各方案详细评估

### 3.1 S0 维持现状（E.1 已实施）

**内容**：`DuckDBWriter` 单写者 + 进程内写锁；读路径 `read_only=True` 连接池；批量 COPY；股票/期货分库；`lock_configuration=true`。

**评价**：已显著缓解同进程内并发写与写时读，但两个遗留未解：
- 演化进程长期持写锁（根因 1）→ 只读也被锁，登记为远期遗留
- 跨进程写协调缺失（根因 2）→ scripts 与 scheduler 仍可能互抢

| 维度 | 得分 | 说明 |
|:-----|:----:|:-----|
| 并发根治度 | 2/5 | 同进程内消除，跨进程与长期持锁未解 |
| 性能 | 5/5 | 完全保留 DuckDB 分析能力 |
| 迁移成本 | 0/5 | 无（已实施） |
| 风险 | 1/5 | 最低（已稳定运行） |
| 运维依赖 | 0/5 | 无新增 |
| 与现状衔接 | 5/5 | 完全一致 |

### 3.2 S1 根治连接生命周期（不换库）⭐ 低风险根治

**内容**：
1. **写连接短生命周期**：写操作执行完立即 `close()`，不再保留进程级写单例。批量写仍用 `executemany`/`COPY` 一次提交。
2. **演化进程读改写分离**：演化/组合进程全程 `read_only=True` 读，仅在晋升/保存等写点短暂开写连接（秒级）写完即关。
3. **跨进程写互斥**：写入口统一经 `filelock`（跨进程文件锁，`data/.locks/*.duckdb.lock`）规范化，写窗口串行化；重试保留作最后兜底。
4. **调度器库级串行**（E.1 §2.3 已设计未完全落实）：同库写 job 不并行。

**针对根因**：1→根因 1，2→根因 1，3→根因 2。DuckDB 固有锁窗口（根因 3）因写连接存活时间从小时级降到秒级而基本不可感知。

**风险点**：连接重建开销（DuckDB connect 内存库毫秒级、文件库首次加载数秒）；`data_futures.py` 属受保护数据层，需专项改造 + 回归。

| 维度 | 得分 | 说明 |
|:-----|:----:|:-----|
| 并发根治度 | 4/5 | 写锁存活降至秒级，跨进程协调补齐 |
| 性能 | 5/5 | 保留 DuckDB，读路径完全不受影响 |
| 迁移成本 | 2/5 | 集中 `data_futures.py` + 演化/调度器连接管理，数据零迁移 |
| 风险 | 2/5 | 受保护数据层改动，需专项回归 |
| 运维依赖 | 0/5 | 无新增 |
| 与现状衔接 | 4/5 | 只改连接管理，不动 SQL 与业务逻辑 |

### 3.3 S2 L4 状态库换 SQLite ⭐ 高性价比局部替换

**内容**：`StateKVStore` 后端从 DuckDB 换 SQLite（WAL + 事务），`state_kv`/`state_history` 双表语义不变，调用方 API 不变（`upsert/get/get_all/snapshot/history`）。

**适配性论证**：
- L4 是**高频小写 + KV 语义**，无 OLAP 查询需求（无聚合分析），SQLite 读写吞吐完全够用
- SQLite WAL：**多读单写不互斥**，写事务短促，天然适配"演化进程高频 save + 外部只读对账"
- **零新依赖**（`sqlite3` 标准库），项目已用 SQLite 做模拟仓（`SimSQLiteStore`），有先例
- 消除 L4 这一个库的全部文件锁冲突——它是当前最活跃、冲突最频繁的库

**代价**：`state.duckdb` 34.8MB 数据迁移（一次脚本导出导入）；部分 SQL（如 `ON CONFLICT DO UPDATE`、JSON 类型）需改写为 SQLite 方言；`seq` 自增改 SQLite `AUTOINCREMENT` 语义。

| 维度 | 得分 | 说明 |
|:-----|:----:|:-----|
| 并发根治度 | 4/5 | L4 库彻底无 DuckDB 锁；WAL 读写并发好 |
| 性能 | 4/5 | KV 场景 SQLite 足够；无 OLAP 需求 |
| 迁移成本 | 2/5 | 单库单模块，数据迁移一次脚本 |
| 风险 | 2/5 | 方言改写需测试覆盖，回退需保留旧库 |
| 运维依赖 | 0/5 | 零依赖 |
| 与现状衔接 | 4/5 | API 不变，调用方零改动 |

### 3.4 S3 全量换 PostgreSQL

**内容**：L2/L3/L4 全部迁至 PostgreSQL，应用层改用连接池/事务。

**评价**：
- 并发根治度最高（真 MVCC、行级锁、连接池），多用户/多机共享场景的唯一正解
- **但 FTS 是本地单机量化工具**，引入 PostgreSQL 服务端 = 安装、启动、账号、备份、端口运维
- 全链路 SQL 方言差异大（DuckDB 的 `read_parquet`、JSON、`ON CONFLICT` 与 PG 差异），L2 行情加载、冷归档 Parquet 读取全部重写
- 性能：单机分析场景 PG 大概率**不如 DuckDB**（无列式向量化，K线全量扫描慢）

| 维度 | 得分 | 说明 |
|:-----|:----:|:-----|
| 并发根治度 | 5/5 | 行级锁 + MVCC，彻底 |
| 性能 | 3/5 | OLAP 弱于 DuckDB，回测数据加载退化风险 |
| 迁移成本 | 5/5 | 最大：全链路 SQL 重写 + 服务运维 |
| 风险 | 4/5 | 高：方言差异、Parquet 衔接断裂、回归面大 |
| 运维依赖 | 5/5 | 引入服务端运维 |
| 与现状衔接 | 1/5 | 需重写存储层与大量查询 |

### 3.5 S4 L2 行情 Parquet 化冷层 + 原子替换写

**内容**：不可变追加数据（K线/分钟）写临时文件 + `os.replace` 原子替换，冷层已 Parquet 化（plans/29 P3-B 已落地冷归档）。

**评价**：
- 解决 L2 写锁，但**查询引擎仍需 DuckDB**（`read_parquet` 原生读），即"不用 DuckDB 写"≠"不用 DuckDB"
- 热层（近 200MB 频繁追加）仍建议保留 DuckDB 热表 + 定期冷却
- 与 S1 组合：写连接短生命周期后，L2 写锁窗口本就极小，本方案增量收益有限

| 维度 | 得分 | 说明 |
|:-----|:----:|:-----|
| 并发根治度 | 3/5 | 写侧无锁，读侧仍需 DuckDB 引擎 |
| 性能 | 4/5 | 保留查询性能 |
| 迁移成本 | 3/5 | 写路径改造 + 冷热分层逻辑 |
| 风险 | 2/5 | 原子替换语义需测试覆盖 |
| 运维依赖 | 0/5 | 无新增 |
| 与现状衔接 | 3/5 | 冷层已 Parquet，热层需改造 |

### 3.6 S5 完全弃用 DuckDB（Polars/SQLite 替代）

**内容**：移除全部 DuckDB 依赖，分析查询改 Polars 或 SQLite。

**评价（诚实评估）**：
- **技术可行，但代价与收益严重失衡**：
  - `fts_history.duckdb` 195MB K线库：改 Polars 需重写全部 SQL 查询（回测引擎、因子加载、CLI 查询数十处），改 SQLite 分析性能退化 1~2 个数量级
  - 信号缓存 Parquet 读写、冷归档读取目前依赖 DuckDB 原生能力（项目明确记录 pyarrow 未装、用 duckdb 原生读写 Parquet），弃用后需补 pyarrow 依赖 + 重写缓存层
  - L3 因子目录的 SQL 查询（`factor_catalog` 关联 `factor_evaluations`/`factor_versions` 等 8 表）在 SQLite 下需手工建索引与改写 JOIN
  - **弃用后 S1 的根因 1/2 问题依然存在**——连接生命周期不根治，Polars 写 Parquet 同样会踩文件并发
- 结论：S5 是**为消除锁而牺牲分析引擎**，不符合 FTS 以量化分析为核心价值的定位。仅在根因 1/2 已根治但 DuckDB 固有锁窗口（根因 3）仍不可接受时才值得二次评估。

| 维度 | 得分 | 说明 |
|:-----|:----:|:-----|
| 并发根治度 | 3/5 | 换引擎不解决生命周期问题，根因 1/2 仍在 |
| 性能 | 1/5 | 分析能力大幅退化 |
| 迁移成本 | 5/5 | 最大：全链路重写 |
| 风险 | 5/5 | 最高：回测引擎/缓存层/查询全链路 |
| 运维依赖 | 1/5 | 新增 pyarrow 等依赖 |
| 与现状衔接 | 0/5 | 破坏性替换 |

## 5. 推荐路线

### 5.1 结论

**弃用 DuckDB（S5）不可取**：它是 FTS 的分析引擎核心，且不解决锁问题的真正根因（连接生命周期）。**PostgreSQL 全量替换（S3）过度**：本地单机工具引入服务端运维。

**推荐 S1 + S2 组合分阶段实施**：

```
阶段 1（S2，先做低风险高收益）：L4 状态库迁 SQLite
  └─ 收益：当前冲突最频繁的库彻底脱离 DuckDB 锁；零依赖；API 不变
阶段 2（S1，根治主因）：写连接短生命周期 + 演化进程只读 + filelock 写互斥
  └─ 收益：L2/L3 写锁存活从小时级降至秒级；跨进程写协调补齐
阶段 3（可选）：L2 热层按需引入原子替换写（S4），进一步压缩写锁窗口
```

### 5.2 各库最终目标态

| 库 | 目标后端 | 理由 |
|:---|:---------|:-----|
| `data/fts_history.duckdb` | **DuckDB（保留）** | 分析引擎核心，S1 后写锁窗口秒级 |
| `data/factor_catalog_{stock,futures}.duckdb` | **DuckDB（保留）** | 低频写，S1 后无冲突 |
| `data/state.duckdb` | **SQLite（迁移）** | 高频小写 KV，WAL 天然适配 |
| `memory/cache/factor_signals/*.parquet` | **Parquet（不变）** | 引用缓存，DuckDB 原生读写 |

### 5.3 决策门槛（S5 何时才值得重新评估）

仅在以下条件同时成立时重新评估 S5：
1. 根因 1/2 已根治（S1+S2 完成），但 DuckDB 固有锁窗口仍造成不可接受的阻塞
2. 分析性能可通过 Polars/Arrow 达到同等水平（需基准验证）
3. 有明确的团队/环境因素排除 DuckDB（如许可证、部署形态约束）
